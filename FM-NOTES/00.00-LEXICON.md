## PART 1: UNIFIED & CROSS-IDE BOUNDARY FILES

### 1. `.aiexclude` (Root file)
*   **What it is:** A hardcoded safety security manifest containing file-matching patterns (e.g. `**/*.key`, `credentials/`).
*   **Why it matters:** It prevents reasoning models and automated sub-agents from reading sensitive corporate variables, secrets, or certificates.
*   **How it functions:** Intercepted at the physical file-system layer by the local Model Context Protocol (MCP) server before any file read/write tool call is resolved. If a requested path matches `.aiexclude`, the MCP server aborts the action, returning an `IO_ACCESS_DENIED` error.

### 2. `.geminiignore` (Root file)
*   **What it is:** An ingestion filter configuration file that dictates which files/directories the Google Antigravity IDE drops from its reasoning buffers.
*   **Why it matters:** Prevents token bloat, context saturation, and background watcher racing by ignoring bulky data formats (e.g., `.csv`, `.xlsm`, `.xlsx`, `.pdf`) and temporary folders.
*   **How it functions:** Evaluated during agent ingestion initialization. Matches are dropped from the active memory representation before the agent maps workspace contents.

### 3. `.gitignore` (Root file)
*   **What it is:** A standard Git version control configuration file that blocks local metadata, caches, and state logs from being uploaded to repositories.
*   **Why it matters:** Keeps the shared codebase clean and protects local workstation configurations from causing conflicts for other users.
*   **How it functions:** Parsed by the Git engine, preventing untracked folders like `.state/`, `.agents/states/`, `logs/`, and `temp/` from being staged for commits.

### 4. `GEMINI.md` (Root file)
*   **What it is:** An adapter ruleset providing baseline instructions specifically for the Google Antigravity environment.
*   **Why it matters:** Directs the model's persona when running inside Antigravity, acting as a sister file to VS Code's `AGENTS.md`.
*   **How it functions:** Injected as a core system constraint, setting the model to act as a non-conversational, high-level architect.

### 5. `AGENTS.md` (Root file)
*   **What it is:** The global meta-rules and role definition agreement file for the VS Code Codex agent.
*   **Why it matters:** Restricts the model to a strict engineer-level delivery mode, eliminating conversational greetings ("fluff") and ensuring data formatting fidelity.
*   **How it functions:** Loaded as the primary instructions for any sub-agent workflow, establishing rules like raw plain text formatting for numerical tables.

### 6. Model Context Protocol (MCP) Bridge
*   **What it is:** A standardized JSON-RPC link that connects models to local terminal execution environments and file systems.
*   **Why it matters:** Enforces boundary checks, preventing models from executing arbitrary OS terminal commands without user review.
*   **How it functions:** Standard terminal and file tools route requests through a local MCP server wrapper that intercepts and filters the arguments.

### 7. Watcher State Racing
*   **Definition:** An infinite read-write feedback loop where file watchers in IDE A and IDE B repeatedly trigger updates based on the other's generated metadata.
*   **Prevented Risk:** High CPU usage, drive lockups, and workspace tool failures.
*   **Mitigation:** Symmetrical directory exclusion filters set in `.vscode/settings.json` and `.geminiignore`.

## PART 2: THE GOOGLE ANTIGRAVITY SPECIFICATION (`.agents/` & `.gemini/`)

### 1. `.gemini/GEMINI.md`
*   **What it is:** The core rules file for the Antigravity state manager agent.
*   **Why it matters:** It defines the workspace as a meta-state vault, forcing the agent to focus purely on planning and state tracking rather than compilation.
*   **How it functions:** Pre-pended to every Antigravity user session request.

### 2. `.agents/rules/global.md`
*   **What it is:** The baseline precedence ruleset governing system shell interactions.
*   **Why it matters:** Enforces the absolute rule hierarchy: `DENY > ASK > ALLOW`. Ensures local workspace variables cannot loosen security rules.
*   **How it functions:** Checked prior to launching any sub-agent terminal context.

### 3. `.agents/skills/base-validator/SKILL.md`
*   **What it is:** A declarative instruction package mapping capability triggers, parameters, and python scripts for data validation.
*   **Why it matters:** Implements progressive context loading—ensuring syntax checking rules are only loaded when validating data, keeping the main context window clean.
*   **How it functions:** Triggered when the agent encounters keywords defined in the YAML header of the skill.

### 4. `.agents/skills/base-validator/scripts/validate_data.py`
*   **What it is:** A python script that runs deterministic syntax verification over tabular files.
*   **Why it matters:** Serves as a sandbox checker that returns success or traceback blocks to the auditor agent.
*   **How it functions:** Called programmatically by the active skill wrapper.

### 5. `.agents/workflows/01_genesis_prompt.md`
*   **What it is:** The bootstrap compiler workflow that takes unstructured ideas and maps them into architectural matrices.
*   **Why it matters:** Standardizes project startup, mapping target stacks, constraints, and failures.
*   **How it functions:** Copied into a stateless chat window. The output is saved to `states/[DOMAIN]_V1.0.md`.

### 6. `.agents/workflows/02_entry_and_propose.md`
*   **What it is:** The active session resumption workflow that establishes the **Authorization Hold**.
*   **Why it matters:** Stops the agent from running commands or editing files automatically.
*   **How it functions:** Pasted along with the latest state binary. The agent generates a plan and halts execution until the operator enters the command `APPROVED`.

### 7. `.agents/workflows/03_exit_and_sync.md`
*   **What it is:** The state serialization and ledger integration workflow.
*   **Why it matters:** Packages turn-by-turn modifications, preventing memory degradation over long development schedules.
*   **How it functions:** Copied into the chat window at session end. Block 1 updates the domain's state binary file, and Block 2 appends a summary row to the master index.

### 8. `.agents/states/_ACTIVE_INDEX.md`
*   **What it is:** The master active ledger tracking all ongoing project domains.
*   **Why it matters:** Serves as a single index of domain names, version counters, last modified times, and priority failure risks.
*   **How it functions:** Updated after every session using the table row generated by the Exit workflow.

### 9. `.agents/states/[DOMAIN_NAME]_V*.md`
*   **What it is:** The domain-specific state binary file (e.g. `states/FINANCE_V1.1.md`).
*   **Why it matters:** Acts as the persistent "memory" of a project, completely bypassing chat history degradation.
*   **How it functions:** Injected during the Entry workflow to restore the model's environment context.

### 10. `.agents/states/README_GUIDE.md`
*   **What it is:** The operational system field manual describing the triple-stage session lifecycle.
*   **Why it matters:** Provides developers with step-by-step instructions on how to handle the serialization loop without losing context.
*   **How it functions:** Consulted manually by the developer to manage state changes.

## PART 3: THE VS CODE & GPT / CODEX SPECIFICATION (`.codex/` & `.vscode/`)

### 1. `.codex/config.toml`
*   **What it is:** The runtime configuration profiles for the VS Code Multi-Agent orchestrator.
*   **Why it matters:** Dictates the token thresholds, confidence ratings, and commands explicitly blacklisted from execution (e.g. `rm`, `sudo`, `curl`).
*   **How it functions:** Evaluated during Codex extension startup to apply constraints on context size and terminal interactions.

### 2. `.codex/instructions.md`
*   **What it is:** VS Code-specific guideline extensions detailing target paths and local project assumptions.
*   **Why it matters:** Keeps the Codex agent aligned with editor-specific tasks without cluttering global files.
*   **How it functions:** Appended to the system context of the Codex interpreter loop.

### 3. `.codex/agents/` (Directory)
Contains agent configuration profiles:
*   `code_reviewer.toml`: Models the style checker agent, focusing on code formatting, standards, and syntax consistency.
*   `test_runner.toml`: Configures the testing agent, focusing on executing scripts and analyzing test coverages.
*   `documentation_writer.toml`: Sets formatting rules for structural documentation.
*   `security_auditor.toml`: Configures the sandbox scanner to inspect command scripts for vulnerabilities.

### 4. `.codex/skills/` (Directory)
Stores procedural manuals loaded into Codex context only when specific task patterns are triggered:
*   `coding_standards.md`: Code style guides and syntactic requirements.
*   `validation.md`: Mappings of file validations and checks.
*   `testing.md`: Execution guides for unit and regression checks.
*   `release_review.md`: The release review checklists that block credentials leakage.

### 5. `.vscode/settings.json`
*   **What it is:** Workspace configuration controlling search indexing boundaries and code auto-formatting.
*   **Why it matters:** Keeps the editor's indexing engine light by hiding logs, caches, and states from searches.
*   **How it functions:** Read directly by VS Code on startup to scope the workspace scanner.

### 6. `.vscode/tasks.json`
*   **What it is:** Workspace configurations that compile automation commands into the VS Code task panel.
*   **Why it matters:** Provides one-click triggers for python scripts, schema checkers, and index sync scripts, eliminating manual command syntax.
*   **How it functions:** Executed by selecting `Terminal -> Run Task` within the VS Code editor.

### 7. `.vscode/extensions.json`
*   **What it is:** Manifest listing recommended plugins for the workspace.
*   **Why it matters:** Prevents syntax inconsistencies by prompting the developer to install identical linters, markdown viewers, and compilers.
*   **How it functions:** Read by VS Code to suggest matching extensions to developers.

### 8. `.vscode/launch.json`
*   **What it is:** Configurations for debugging local application components.
*   **Why it matters:** Allows developers and testing agents to step through execution logic line-by-line.
*   **How it functions:** Accessed via the debug panel to launch validators with the debugger attached.

### 9. `.state/BASELINE.md`
*   **What it is:** The immutable ground truth log of initial project constants.
*   **Why it matters:** Acts as a contract for the project's baseline parameters, preventing the model from re-designing architecture.
*   **How it functions:** Read at start of work to verify initial conditions.

### 10. `.state/DELTA_LOG.md`
*   **What it is:** Chronological ledger detailing every incremental system change.
*   **Why it matters:** Records the date, tasks executed, files modified, and resulting state hashes.
*   **How it functions:** Appended to after completing tasks to maintain a history of workspace updates.

### 11. `.state/DECISIONS.md`
*   **What it is:** Record of locked architectural decisions.
*   **Why it matters:** Stops the agent from suggesting modifications that violate locked rules (e.g. changing dynamic variables or network paths).
*   **How it functions:** Queried by the planning engine to block unaligned design paths.

### 12. `.state/TRACE_INDEX.md`
*   **What it is:** The mapping index linking validators and test logs.
*   **Why it matters:** Tracks automated test validation logs back to specific change records.
*   **How it functions:** Referenced dynamically to review validation evidence.

### 13. `validators/validate_structure.py`
*   **What it is:** Python checking script verifying file layout structure.
*   **Why it matters:** Proves the directory matches the architectural specifications before modifications start.
*   **How it functions:** Executed programmatically; fails and prints missing folders if the directory structure drifts.

### 14. `validators/validate_config.py`
*   **What it is:** Python validator checking target paths and system configurations.
*   **Why it matters:** Prevents execution errors due to invalid file paths or missing variables.
*   **How it functions:** Evaluates the operating system paths to guarantee configurations are correct.

### 15. `validators/validate_tests.py`
*   **What it is:** The programmatic wrapper executing the unit and regression test suites.
*   **Why it matters:** Guarantees new code does not introduce errors into existing modules.
*   **How it functions:** Runs tests and formats the output into standard logging tables.

### 16. `validators/validate_release.py`
*   **What it is:** The final gatekeeper script verifying the project configuration before packaging.
*   **Why it matters:** Verifies tests, structural requirements, and state logs, while ensuring no secrets are packaged in the final product.
*   **How it functions:** Invoked by VS Code tasks as the final verification step.
